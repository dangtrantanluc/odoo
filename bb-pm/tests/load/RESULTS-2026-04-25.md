# Load test baseline — 2026-04-25

First baseline run on dev hardware after Phase 4 added k6 scripts and
Phase 1 plumbing was live. Captured here so future runs have a number
to regress against.

## Hardware

- Local dev box (Linux 6.8, single Postgres container on tmpfs would be faster).
- Postgres 16-alpine in Docker, default config, port 5433.
- bb-pm API in `tsx watch` mode (NOT production build — production should be a touch faster).
- 28 audit log rows + 11 follow-up rows + small fixture (~10 tasks) at run time.

## Read endpoints — `agent-api.js`

20 VUs ramped over 80s, 4 endpoints per iteration.

| Metric | Value |
|---|---|
| Total requests | 13,836 |
| RPS | 172 |
| Errors | 0% |
| `overdue` p95 | 6.25 ms |
| `digest` p95 | 8.22 ms |
| `audit_list` p95 | 3.36 ms |
| `audit_stats` p95 | 2.55 ms |
| Overall p95 | 7.07 ms |

All thresholds (p95 < 500ms reads, < 800ms stats) pass with 60–300×
headroom. Headroom suggests the API isn't the bottleneck — at higher
VU counts we'd hit Node event-loop saturation before the DB.

## Write endpoint — `follow-up-write.js`

5 VUs, 20s constant.

| Metric | Value |
|---|---|
| Total requests | 20,012 |
| RPS | 1000 |
| Errors | 0% |
| p95 | 6.24 ms |
| Max | 27.5 ms |

The write path goes through 2 FK lookups (task, user) + 1 INSERT into
`agent_follow_ups`. 1000 writes/sec at 5 VUs is more than we'll ever
need — production load is closer to **dozens of follow-ups per day**.

## Issue surfaced + fix

First read run produced 95.8% HTTP failures. Cause: the global
`@fastify/rate-limit` plugin was set to 300 req/min and was rejecting
every burst above ~5 RPS. Internal agent traffic doesn't deserve to
share that budget — the OpenClaw plugin already rate-limits
`/agent/run` upstream.

Fix in [server.ts](../../apps/api/src/server.ts): add `allowList: (req)
=> !!req.headers["x-agent-token"]` so the agent service user bypasses
the plugin's bucket. Web/JWT users still hit the 300/min limit.

After the fix, error rate dropped from 95.8% to 0% with the same load.

## Not measured

- `POST /agent/run` end-to-end. LLM (Qwen) dominates that latency
  (seconds, not milliseconds) and our concern there is throughput at
  the LLM provider, not at the API. Add a separate script paced to LLM
  TPS when needed.
- Concurrent writes + reads contending on `agent_audit_log`. Inserts
  are fire-and-forget today; if they ever block a tool call, this is
  where to look.
- Cron-driven digest scan against a real-size DB (50+ projects, 5000+
  tasks). Test fixture is tiny.

## Re-run

```sh
TOKEN=$(grep AGENT_API_TOKEN /home/bbsw/pm/bb-pm/.env | cut -d= -f2)
k6 run -e TARGET=http://localhost:4000/api/v1 -e AGENT_TOKEN=$TOKEN \
  bb-pm/tests/load/agent-api.js
k6 run -e TARGET=http://localhost:4000/api/v1 -e AGENT_TOKEN=$TOKEN \
  -e TASK_ID=1 -e USER_ID=3 \
  bb-pm/tests/load/follow-up-write.js
```
